# 02. 사용자·권한·계정 보안

## 1. 권한의 두 가지 축 (확정)

권한은 두 가지로 나눠 관리한다.

- **열람 범위**: 어느 팀 화면을 볼 수 있는가
- **수정 권한**: 데이터를 입력·수정할 수 있는가

## 2. 역할별 권한표 (확정)

| 사용자 | 열람 범위 | 수정 권한 | 관리자 페이지 |
|---|---|---|---|
| 대표 | 전체 | 전체 | 사용 가능 |
| 경영지원팀 | 전체 | 전체 | 사용 가능 |
| 관리자 | 전체 | 전체 | 사용 가능 |
| 생산팀 팀장 | 생산팀 화면 | 생산팀 데이터 | 없음 |
| 생산팀 팀원 | 생산팀 화면 | 없음(열람만) | 없음 |
| 서비스팀 팀장 | 서비스팀 화면 | 서비스팀 데이터 | 없음 |
| 서비스팀 팀원 | 서비스팀 화면 | 없음(열람만) | 없음 |

- **겸직 처리 (확정)**: 생산팀과 서비스팀은 사실상 같은 직원이 두 팀 일을 함께 맡는다. 한 사람에게 여러 팀을 지정할 수 있게 하고, 두 팀 직원은 기본으로 두 화면을 모두 열람한다.
- (확인 필요) 두 팀의 팀장이 한 명인지, 두 팀의 수정 권한을 같은 사람이 갖는지.
- (확인 필요) 팀원이 실적을 직접 입력할 일은 없는지.

## 3. 사용자 모델 (확정 + 제안)

- **확정**: `AbstractUser`를 상속받아 확장한다. 아이디, 비밀번호(자동 해시 저장), 이름, 로그인 기록 등 기본 기능을 그대로 쓴다.
- **(제안)** 사용자 모델은 **하나만** 만든다. Django는 로그인에 쓰는 사용자 모델을 하나만 지정할 수 있기 때문이다.
- **(제안)** 12명 규모이므로 복잡한 권한 시스템 대신 "사용자 테이블에 역할과 소속 팀 목록을 저장"하는 단순한 구조로 시작한다.

### 추가 필드 (제안)

| 필드 | 뜻 | 값 |
|---|---|---|
| `role` | 역할 | `ceo`(대표), `management`(경영지원팀), `admin`(관리자), `leader`(팀장), `member`(팀원) |
| `view_teams` | 열람 가능한 팀 화면 (여러 개 선택) | `production`(생산팀), `service`(서비스팀) |
| `edit_teams` | 수정 가능한 팀 데이터 (여러 개 선택) | `production`, `service` |
| `must_change_password` | 첫 로그인 시 비밀번호 변경 안내 여부 | 계정 발급·초기화 시 `True`, 변경 후 `False` |

- `ceo`, `management`, `admin`은 팀 필드와 관계없이 **전체 열람·전체 수정·관리자 페이지 사용**이 가능하다.
- `leader`는 기본값으로 소속 팀을 `view_teams`와 `edit_teams`에 넣고, `member`는 `view_teams`에만 넣는다.
- 관리자 페이지에서 직원별로 `view_teams`, `edit_teams`를 체크박스로 등록·해제한다.
- 이름은 `AbstractUser`의 기본 필드를 사용한다. 구체적인 필드 저장 방식(배열 필드 또는 별도 테이블)은 1주차에 팀이 정한다.
- **결정 (2026-10-18)**: `view_teams`, `edit_teams`는 PostgreSQL `ArrayField`(목록 한 칸에 여러 값을 저장)로 만든다. 12명 규모라 별도 테이블은 과하다. 구현: `backend/accounts/models.py`

### 설정 주의

- `settings.py`에 `AUTH_USER_MODEL = "accounts.User"`(앱 이름은 팀 결정)를 **첫 `migrate` 전에** 설정한다.

## 4. 권한 확인 규칙 (제안)

- 백엔드 API에서 요청마다 열람·수정 권한을 확인한다. 화면에서 메뉴·버튼을 숨기는 것만으로는 부족하다.
- 열람 권한이 없는 팀 화면 주소로 직접 들어오면 접근을 막고 안내한다.
- 수정 권한이 없는 사용자에게는 입력·업로드 버튼을 보여주지 않는다.
- 경영지원팀 메인 화면의 열람 범위: 권한표상 "전체" 열람은 대표·경영지원팀·관리자다. (확인 필요) 팀장·팀원이 메인 화면을 볼 수 있는지는 지침에 명시되어 있지 않다.

## 5. 계정·보안 (확정 + 기본 원칙)

회원가입 기능은 만들지 않는다.

| 기능 | 내용 |
|---|---|
| 계정 발급 | 경영지원팀(관리자)이 아이디와 초기 비밀번호를 일괄 부여한다 |
| 비밀번호 변경 | 각 직원이 로그인 후 본인 비밀번호를 바꿀 수 있다 |
| 비밀번호 초기화 | 비밀번호를 잊은 직원은 관리자가 초기화해 준다. 이메일 인증 같은 복잡한 기능은 만들지 않는다 |
| 첫 로그인 안내 | 첫 로그인 시 비밀번호 변경을 안내한다 |

- (기본 원칙) 비밀번호는 원문이 아니라 해시로 저장한다. Django의 `set_password()`를 사용한다.
- **(제안) 비밀번호 규칙**: 8자 이상 + 영문·숫자·특수기호 각 1개 이상(KISA 권고: 3종류 조합 8자 이상). 특수기호는 키보드 ASCII 특수기호 32개 ``!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~``만 허용하고 공백·한글은 금지. 흔한 비밀번호·숫자만·아이디와 비슷한 비밀번호도 금지(Django 기본 규칙). 화면에 규칙과 특수기호 목록을 표시하고, 입력하는 동안 지킨 규칙에 ✔ 표시. 구현: `backend/accounts/validators.py`, `frontend/src/passwordRules.js`
- (기본 원칙) 실제 기업 데이터, 계정 정보, API 키는 GitHub 등 외부에 올리지 않는다.
- 로그인 방식(세션 인증 / JWT)은 1주차에 팀이 하나로 정한다. → [01-architecture.md](01-architecture.md)

## 6. 관리자 페이지 (확정)

대표·경영지원팀·관리자만 사용한다.

| 기능 | 내용 | 우선순위 |
|---|---|---|
| 계정 발급 | 아이디, 이름, 초기 비밀번호, 역할, 소속 팀 입력 | 핵심 |
| 권한 등록·해제 | 직원별 열람 범위·수정 권한을 체크박스로 선택 (제안) | 핵심 |
| 비밀번호 초기화 | 선택한 직원의 비밀번호를 초기 비밀번호로 재설정 | 핵심 (어려우면 이것부터) |

### 화면 구성 (제안)

- 직원 목록 표: 아이디, 이름, 역할, 열람 범위(생산팀·서비스팀 체크박스), 수정 권한(생산팀·서비스팀 체크박스), [비밀번호 초기화] 버튼
- [계정 발급] 버튼 → 입력 폼
